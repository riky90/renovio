# Phase 08.1: Catalogo domande — pagina CRUD e file Excel — Research

**Researched:** 2026-09-23

## Summary

This phase does not introduce a new import/export mechanism — Fase 08's registry (`backend/app/services/import_excel/registry.py`) already supports a **single resource spanning five sheets** (`parametri` does exactly this today: `moltiplicatori`, `listino_categoria`, `extra`, `coefficienti_pro`, `forfait_arredo`, one Python module, one `HANDLER["parametri"]` entry). The minimal extension is: add `HANDLER["domande"]` via a new `backend/app/services/import_excel/domande.py` module structured identically to `parametri.py`, and a new `backend/app/services/export_excel/domande.py` structured identically to `export_excel/parametri.py`, plus one new `GET /admin/domande/export.xlsx` endpoint in the existing `routers/admin/domande.py`. **No registry code changes are needed** — `registra()`/`risolvi_handler()`/`HANDLER` are already generic over multi-sheet resources.

The CRUD backend for domande/opzioni/effetti/attese already exists (GET/POST/PATCH, all `require_admin`, all tested) — this phase's backend work is: remove four `DELETE` routes, add two columns (`opzione_domanda.attiva`, `attesa_immobile.attiva`) plus `updated_at` on all five catalog tables via one migration `0020` following the exact three-step pattern of `0019_updated_at_curatela.py` (which **failed on SQLite once already** — the fix is documented and must be replicated verbatim), add a D-28 dependency-guard function before any opzione deactivation (UI toggle AND Excel import), and auto-create the implicit `code='valore'` option when a `stepper`/`numero` domanda is created (currently done only by the seed JSON, never by the API — this is new code).

Frontend is a new page reusing existing components with zero new shadcn installs and zero new library dependencies. The one real frontend gap is that `apiPatch`/`apiPost`/`apiGet`/`apiDelete` (both `api/client.ts` and `api/admin/client.ts`) discard the backend's `detail` on error — this must be fixed for D-28's per-dependency rejection message to reach the toast.

**Primary recommendation:** structure the entire phase as "one more resource in an already-generic system," not as new infrastructure. Every file this phase creates has a same-shape sibling already in the repo (`parametri.py` ×2, `lead.py`, `0019`, `ExtraTab`, `ListiniPage`) — the planner should assign each task to "copy this pattern," not "design this pattern."

### Pattern 1: Registry resource spanning multiple sheets (answers research question 1)

**What:** `HANDLER: dict[str, ImportHandler]` in `registry.py` maps **one resource name to one handler module**; nothing forces one-sheet-per-resource. `parametri.py` is the existing proof: `RISORSA = "parametri"`, and its `parse()`/`diff()`/`apply()` each internally loop over 5 sheet names (`FOGLIO_MOLTIPLICATORI`, `FOGLIO_LISTINO_CATEGORIA`, `FOGLIO_EXTRA`, `FOGLIO_COEFF_PRO`, `FOGLIO_FORFAIT`), each dispatched to its own `_risolvi_*` resolver function via a `_RESOLVER: dict[str, callable]` lookup by sheet name (not by resource name).

**When to use:** exactly this phase's case — five DB tables, one logical "catalog," one downloadable file, one upload button.

**Recommended shape for `domande` resource** (mirrors `parametri.py` 1:1):
```python
# Source: backend/app/services/import_excel/parametri.py (pattern to replicate)
RISORSA = "domande"
FOGLIO_DOMANDE = "domande"
FOGLIO_OPZIONI = "opzioni"
FOGLIO_EFFETTI = "effetti"
FOGLIO_ATTESE = "attese"
FOGLIO_DERIVAZIONI = "derivazioni"

_RESOLVER = {
    FOGLIO_DOMANDE: _risolvi_domanda,
    FOGLIO_OPZIONI: _risolvi_opzione,
    FOGLIO_EFFETTI: _risolvi_effetto,
    FOGLIO_ATTESE: _risolvi_attesa,
    FOGLIO_DERIVAZIONI: _risolvi_derivazione,
}

class _DomandeHandler:
    ruolo_richiesto = "admin"
    parse = staticmethod(parse)
    diff = staticmethod(diff)
    apply = staticmethod(apply)

registra(RISORSA, _DomandeHandler())
```
Import this module for its side effect in `routers/admin/import_excel.py` next to the two existing `# noqa: F401` imports (`import app.services.import_excel.domande  # noqa: F401`) — that line is the **entire** router wiring needed; `POST /admin/import-excel/domande/preview|confirm` starts working automatically because the router is already generic over `{risorsa}`.

**Export side is NOT registry-based** (verified: `export_excel/*.py` has no registry, each resource gets its own `GET .../export.xlsx` route calling its own `build_workbook_*()` function directly). Model `build_workbook_domande(db) -> tuple[bytes, int]` on `build_workbook_parametri`, and add one `@router.get("/export.xlsx")` in `routers/admin/domande.py` (same shape as `routers/admin/coefficienti.py:91-113`, including the `ExportLog(risorsa="domande", ...)` write before the response — CUR-04/D-15).

### Pattern 2: Natural-key vs. surrogate-key resolution per sheet (answers research question 2)

Every existing resolver in `parametri.py` follows the same shape: **try `id` first (numeric `db.get(Model, id)`), then fall back to a natural-key lookup for row creation only.** The five domande sheets map onto three already-proven variants:

| Sheet | DB reality | Recommended `id` semantics | Model to copy |
|---|---|---|---|
| `domande` | PK is `Domanda.code` (string, no numeric id) | `id` column holds `Domanda.code` itself; read with `leggi_foglio_piatto(..., id_numerico=False)` (exists today, used by `extra`). Row **without** `id` = scarto ("il code e' sempre richiesto" — same message class as `_risolvi_extra`). Row **with** an `id`/code not found in DB = **new domanda** (same as `_risolvi_extra`: `db.get(Extra, code)` is `None` → creation branch, not a scarto — only a *missing* id column is a scarto). A `code` **changed** in the file simply doesn't match any row → resolves to "new domanda under the new code," and the old code's row is untouched (matches CONTEXT.md's expectation: "scarto descritto, non rinomina" — more precisely here it's "create sotto il nuovo code, il vecchio resta" since D-03/D-04 always allow row-without-id-match = new, this is consistent, not a special case) | `_risolvi_extra` in `parametri.py:301-359` |
| `opzioni` | Surrogate `OpzioneDomanda.id` (autoincrement) **+** DB-enforced natural key `UniqueConstraint(domanda_code, code)` | `id` numeric first (`db.get(OpzioneDomanda, id)`); row without `id` resolves via natural key `(domanda_code, code)` — create only if the parent `domanda_code` exists (`db.get(Domanda, domanda_code)`), exact same two-tier shape as `_risolvi_moltiplicatore` | `_risolvi_moltiplicatore` in `parametri.py:157-195` |
| `effetti` | Surrogate `EffettoOpzione.id` **only** — genuinely no natural key (CONTEXT.md is correct) | `id` numeric first. Row without `id` = **new effetto**, but needs an explicit `opzione_id` column in the sheet (numeric, like `forfait_arredo`'s `opzione_id`) to know its parent — there is no alternative reference, since there's no natural key. Context columns `domanda_code`/`opzione_code` (read-only, ignored on import, same convention as `voce_descrizione`/`opzione_etichetta`) make the sheet human-readable without becoming part of the identity | `_risolvi_forfait` in `parametri.py:432-496` (id + `opzione_id` as one of the natural-key columns for *lookup*, though here `opzione_id` alone doesn't disambiguate — a new effetto is simply always "new," no natural-key dedup needed, since two effects on the same opzione+tipo+target ARE meant to be distinct in theory, though in practice `valida_effetto` doesn't enforce uniqueness — treat every id-less row with a valid `opzione_id` as a new row, no dedup-by-tuple like `chiavi_nuove` needed unless the planner wants to guard against literal file duplication) |
| `attese` | Surrogate `AttesaImmobile.id` **+** DB-enforced natural key `UniqueConstraint(attributo_code, fascia_mq_min)` | Same two-tier shape as `opzioni`/`moltiplicatori`. This is also the key UI-SPEC §B already names ("`attese`: `attributo_code` + `fascia_mq_min`") — it is the literal DB constraint, not an invented display key | `_risolvi_moltiplicatore` |
| `derivazioni` | Surrogate `DerivazioneRisposta.id` **+** DB-enforced 4-column natural key `UniqueConstraint(domanda_code, quando_opzione_code, da_domanda_code, da_opzione_code)` | Same two-tier shape. UI-SPEC §B names only `id` as the display key for this sheet — that is a valid simplification (four columns is a lot to render as one string) but the *resolution* code should still support the natural-key fallback for id-less new rows, mirroring the DB constraint, since D-06 explicitly wants this sheet to be **the only way** to author derivazioni | `_risolvi_moltiplicatore` |

**Cross-sheet ordering on import:** `parametri.py::parse()` reads all 5 sheets unconditionally in a fixed tuple order and returns one flat `list[RigaPiattaIn]` — order in that list does **not** determine DB write order, because `diff()`/`apply()` resolve each row independently against whatever already exists in the DB (not against other rows in the same file). For `domande`, this matters more than for `parametri` because of real FK dependencies (`opzioni.domanda_code → domanda.code`, `effetti.opzione_id → opzione_domanda.id`). **Recommendation, both new and proven elsewhere:** parse all 5 sheets, but in `apply()`, process them in dependency order — `domande` → `opzioni` → `effetti`/`attese`/`derivazioni` — same discipline `parametri.py::apply()` already uses implicitly for `listino_categoria` (which needs `Listino`/`Categoria` to pre-exist, always true since those aren't imported by this handler) plus the **explicit `db.flush()` after every creation** (`parametri.py:770`, documented as fixing the exact "two new rows with the same natural key in one file" bug found in Fase 08's gap closure, WR-04 in `08-REVIEW-FIX.md`). A new domanda created earlier in the same `apply()` call must be visible (via flush) to the opzione resolver that references its `domanda_code` later in the same call.

**Transactional atomicity:** already given for free by the existing router (`import_excel.py::confirm_import`) — one `db.commit()` after `handler.apply()` returns, with `db.rollback()` in the `except` branches (`IntegrityError`, generic `Exception`). No new transactional code needed; `domande`'s handler just needs to behave like `parametri`'s (no early commits inside `apply()`).

### Pattern 3: SQLite-safe additive migration (answers research question 3)

`0019_updated_at_curatela.py` failed once on SQLite (documented in `.planning/phases/08-export-import-excel/08-REVIEW-FIX.md`, iteration 1, "terzo critico trovato il 2026-09-23") with `Cannot add a column with non-constant default` — the root cause is `ALTER TABLE ... ADD COLUMN ... DEFAULT CURRENT_TIMESTAMP`, which SQLite's `ADD COLUMN` rejects because it only accepts **constant** defaults, and `server_default=func.now()` compiles to a non-constant `CURRENT_TIMESTAMP` expression. `0019`'s fix, which **0020 must replicate verbatim** for the `updated_at` half of its work:

```python
# Source: backend/alembic/versions/0019_updated_at_curatela.py (verbatim pattern to replicate)
for tabella in _TABELLE:
    op.add_column(tabella, sa.Column("updated_at", sa.DateTime(), nullable=True))  # step 1: nullable, no default
    op.execute(sa.text(f"UPDATE {tabella} SET updated_at = :adesso").bindparams(adesso=adesso))  # step 2: backfill
    with op.batch_alter_table(tabella) as batch:  # step 3: tighten via table-rebuild
        batch.alter_column("updated_at", existing_type=sa.DateTime(), nullable=False, server_default=sa.func.now())
```
`batch_alter_table` triggers SQLite's CREATE-new-table/copy/DROP/RENAME dance, and a `CURRENT_TIMESTAMP` default **is** legal inside a fresh `CREATE TABLE`, which is why step 3 works where a direct `ADD COLUMN ... DEFAULT` doesn't.

**Important nuance for `attiva` (boolean, not timestamp):** `opzione_domanda.attiva` and `attesa_immobile.attiva` do **not** need this three-step dance — `Domanda.attiva`/`EffettoOpzione.attivo`/`DerivazioneRisposta.attiva` (all pre-existing columns, created in earlier migrations without incident — confirmed no special-cased migration exists for them) use `server_default="1"`, a **string literal**, which is a constant and `ADD COLUMN` accepts it directly. So `0020` needs **two different techniques in the same file**:
```python
# Booleans: plain add_column, one step, constant default — SAFE on SQLite as-is
op.add_column("opzione_domanda", sa.Column("attiva", sa.Boolean(), nullable=False, server_default="1"))
op.add_column("attesa_immobile", sa.Column("attiva", sa.Boolean(), nullable=False, server_default="1"))

# updated_at on domanda/opzione_domanda/effetto_opzione/attesa_immobile/derivazione_risposta:
# THREE-STEP pattern above, verbatim from 0019
```
**Verification requirement inherited from 0019's incident** (explicitly called out in `08-08-PLAN.md`'s Task 1): the plan must run `.venv/Scripts/python.exe -m alembic upgrade head` against the **real `backend/dev.db`**, not just the ephemeral SQLite the test suite builds via `create_all` — `0019`'s failure was invisible to tests because `test_*.py` fixtures build schema from ORM metadata (`Base.metadata.create_all`), not by replaying migrations. `test_admin_domande.py`'s own `client` fixture does exactly this (`Base.metadata.create_all(bind=engine)`, confirmed at line 43) — so **this test file passing tells you nothing about migration correctness**; only `alembic upgrade head` against `dev.db` does.

**One vs. two migrations (Claude's Discretion in CONTEXT.md):** recommend **one** migration `0020_attiva_updated_at_catalogo.py` — the boolean `add_column`s and the three-step `updated_at` dance are independent DDL operations on different columns, nothing forces separation, and Fase 08 already sets the precedent of bundling multiple unrelated additive changes (export_log + updated_at were separate migrations `0018`/`0019`, but that was because they landed in different plans/waves — this phase is one plan-family, so one migration is more consistent with `0014`'s original bundling of 4 new tables).

**Where ORM `onupdate` lives (answers "where else is updated_at onupdate set"):** exclusively on the model column definition, e.g. `updated_at: Mapped[datetime] = mapped_column(nullable=False, server_default=func.now(), onupdate=func.now())` — verified this is the **only** place across the 9 tables 0019 touched (`grep -c "onupdate=func.now()"` was an explicit acceptance criterion in `08-08-PLAN.md`). No router/service code anywhere manually sets `updated_at` — it is 100% automatic via SQLAlchemy's `onupdate` on any ORM-tracked `UPDATE`. The five domande-catalog models need the identical column declaration added.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multi-sheet Excel resource registration | A second registry, a `{risorsa}/{foglio}` route shape | `HANDLER["domande"]` = one more entry in the existing `registry.py` map | Already proven generic by `parametri` (5 sheets, one resource) |

## Common Pitfalls

### Pitfall 1: Engine/public-catalog queries silently ignore the new `attiva` columns (answers research question 4)
**What goes wrong:** After migration `0020` adds `opzione_domanda.attiva`/`attesa_immobile.attiva`, an admin disabling an option in the CRUD still has it apply its effects in every stima, and a disabled attesa baseline still gets used — because nothing queries the new column.
**Why it happens:** `EffettoOpzione.attivo` was already filtered (`services/effetti.py:500`, pre-existing), which creates a false sense that "the filtering already works everywhere."
**How to avoid — exact locations needing a new `.filter(...)`:**
1. `services/effetti.py::_opzioni_per_domanda`-equivalent is actually named differently — the real query to fix is inside `risolvi_scelte()` at `effetti.py:451-454`: `session.query(OpzioneDomanda).filter(OpzioneDomanda.domanda_code.in_(codici))` → add `OpzioneDomanda.attiva.is_(True)`. This feeds both the Free engine and (per `services/arredo.py`, which imports `risolvi_scelte`) the arredo layer.
2. `services/effetti.py::attese_per_mq()` at `effetti.py:271-274`: `session.query(AttesaImmobile).filter(AttesaImmobile.fascia_mq_min <= mq, AttesaImmobile.fascia_mq_max >= mq)` → add `AttesaImmobile.attiva.is_(True)`. This is consumed by **both** the wizard defaults (`routers/domande.py`) and the motore's baseline — one fix covers both, since they share this one function (confirmed by its own docstring: "doppio uso, ed e' il motivo per cui la tabella e' una sola").

**Warning signs:** a disabled opzione still moving a stima's total in `POST /admin/domande/anteprima`, or still appearing in `GET /api/v1/domande`.

### Pitfall 2: `EffettoAdminOut`/`OpzioneAdminOut`/`AttesaAdminOut` schemas don't yet expose `attiva`
**What goes wrong:** frontend badge/toggle has nothing to bind to.
**Why it happens:** these Pydantic schemas (`schemas/admin_domande.py`) were written before D-27/D-40 existed.
**How to avoid:** add `attiva: bool` to `OpzioneAdminOut`, `OpzioneAdminCreateIn` (default `True`), `OpzioneAdminIn` (optional, for the PATCH toggle), and the same three for `AttesaAdmin*`. `_to_opzione_out`/`_to_attesa_out` in `routers/admin/domande.py` must be updated to pass the new field through.

### Pitfall 3: seed_domande() overwrites `domanda`/`opzione_domanda` every boot — a pre-existing tension this phase inherits, not introduces
**What goes wrong:** `scripts/seed.py::seed_domande()` (docstring at line 525-535, verified) treats `domanda` and `opzione_domanda` as **product structure**, rewritten unconditionally on every boot (`domanda.attiva = d_data.get("attiva", True)` at line 558; every opzione field including a would-be `opzione.attiva` at line 570-574). `effetto_opzione`/`attesa_immobile` are **curatela**, created-if-missing only, never overwritten (line 530-535, 598).
**Why it happens:** this asymmetry predates D-27 — `Domanda.attiva` already exists and is already silently reset to the JSON's value on every deploy if an admin toggled it via the CRUD without a matching change to `seed-domande.json`.
**How to avoid:** this phase does not need to fix this (it is out of scope — the JSON already defaults every `attiva` to `True` via `.get("attiva", True)`, so the practical risk is low: an admin who deactivates a domanda/opzione that the seed JSON doesn't explicitly mark inactive would see it silently reactivate on next deploy). **Flag it explicitly to the planner as a known, pre-existing limitation** that D-27 (extending `attiva` to `opzione_domanda`) inherits verbatim, not one this phase should attempt to fix — fixing seed-vs-curatela ownership for `domanda`/`opzione_domanda` is a larger architectural question outside CUR-01/CUR-02's scope.
**Warning signs:** an admin-deactivated domanda/opzione reappearing active after a deploy.

### Pitfall 4: D-28's dependency guard must run in two places, not one
**What goes wrong:** implementing the guard only in `modifica_opzione` (PATCH) makes it easy to bypass via Excel re-import (D-30 explicitly allows `attiva` changes from Excel too).
**Why it happens:** the two code paths (`routers/admin/domande.py::modifica_opzione`, and the new `import_excel/domande.py::_risolvi_opzione`) are separate functions that both eventually write `OpzioneDomanda.attiva = False`.
**How to avoid:** extract a single `verifica_dipendenze_opzione(db, opzione) -> str | None` (returns the human-readable blocking reason, or `None` if safe to disable) in a shared location (e.g. `services/effetti.py` or a new `services/domande_dipendenze.py`), and call it from **both** `modifica_opzione` (raise `HTTPException(400, reason)`) and the import resolver (append a `ScartoRowOut(motivo=reason)`, per UI-SPEC §B: "non genera un errore che blocca l'intero import — cade nell'accordion scarti"). Concrete query shape (all fields already exist on `DerivazioneRisposta`/`Domanda`, no schema changes needed for this check):
```python
# is_default:
if opzione.is_default: return f"e' la risposta predefinita di {domanda.testo}"
# derivazione attiva, tre colonne indipendenti (vedi services/effetti.py DerivazioneRisposta):
db.query(DerivazioneRisposta).filter(DerivazioneRisposta.attiva.is_(True), or_(
    and_(DerivazioneRisposta.domanda_code == opzione.domanda_code, DerivazioneRisposta.quando_opzione_code == opzione.code),
    and_(DerivazioneRisposta.domanda_code == opzione.domanda_code, DerivazioneRisposta.opzione_code == opzione.code),
    and_(DerivazioneRisposta.da_domanda_code == opzione.domanda_code, DerivazioneRisposta.da_opzione_code == opzione.code),

# visibilita':

                          Domanda.visibile_se_opzione_code == opzione.code).first()
```

### Pitfall 5: D-35's implicit `code='valore'` option is currently only a seed convention, not backend behavior (answers research question 5)
**What goes wrong:** creating a `stepper`/`numero` domanda via the new CRUD form leaves it with **zero** options, and the "click domanda → go straight to effetti" UI (D-35/UI-SPEC §D.1) has no opzione to attach effects to.
**Why it happens:** verified by reading `crea_domanda`/`modifica_domanda` in full — neither references `OPZIONE_VALORE`/`"valore"` anywhere. The `code='valore'` row only exists today because `backend/seed_data/seed-domande.json` explicitly lists it per stepper/numero domanda (confirmed: `seed.py` has no special-case code for it, `OpzioneDomanda(domanda_code=domanda.code, code=o_data["code"])` at line 568 just creates whatever the JSON lists).
**How to avoid:** add an explicit auto-creation step in `crea_domanda` (POST) — after determining `tipo_controllo`, if it's in `CONTROLLI_NUMERICI` (`{"stepper", "numero"}`, from `services/effetti.py`), ensure an `OpzioneDomanda(domanda_code=code, code=OPZIONE_VALORE, etichetta=..., is_default=True)` exists (create if missing — same idempotent-upsert shape the seed itself uses for opzioni). Also handle `modifica_domanda` (PATCH): if `tipo_controllo` is changed **into** `CONTROLLI_NUMERICI` from a choice-type, the same ensure-step must run (a domanda can be edited after creation, and D-36 puts `tipo_controllo` in the editable form fields, not creation-only).
**Warning signs:** a newly created stepper domanda has an empty opzioni list at the point the UI tries to reveal its effetti table.

### Pitfall 7: `apiPatch` error propagation must be fixed in the admin client, not the public one, but both are equally broken (answers research question 7)
**What goes wrong:** the opzione-toggle PATCH call (used by the new page) goes through `frontend/src/api/admin/client.ts::apiPatch` (verified: this is a **separate file** from `frontend/src/api/client.ts::apiPatch` — the admin one re-exports `apiGet`/`apiPost` from the public client but defines its **own** `apiPatch`/`apiPut`/`apiDelete`). Both discard `response.json().detail` identically (`throw new ApiError(response.status, \`PATCH ${path} fallita con status ${response.status}\`)`).
**How to avoid:** fix `apiPatch` in `frontend/src/api/admin/client.ts` (the one actually used by the new page's toggle) using the exact try/catch-on-JSON pattern already proven in `apiPostFile` (`api/client.ts:127-135`) or the standalone `extractErrorDetail` helper already extracted in `frontend/src/api/admin/uploadListino.ts` (referenced and imported by `exportExcel.ts`, confirming it's already designed to be shared). **Minimal scope for this phase:** fix `apiPatch` (needed by the toggle) at minimum; UI-SPEC's dependency note explicitly says "Stessa estensione serve almeno su `apiPatch`" — fixing all four verbs in both files is more consistent (and low-risk, since it's purely additive: today's generic message becomes a fallback only when the body isn't valid JSON or has no `detail`) but only `apiPatch`-in-`admin/client.ts` is load-bearing for this phase's must-haves.
**Who else relies on current (generic) messages:** every existing admin page using `apiPatch`/`apiPost`/`apiDelete` today gets today's generic `"PATCH {path} fallita con status {status}"` string — none of them currently branch on message content (verified no `.message ===` string-matching exists in any admin page's catch block via the shared `ApiError` type), so propagating `detail` is safe: it only ever **replaces** a less-informative string with a more-informative one, never changes control flow.
**Reusable frontend assets confirmed present for §A/§C reuse (UI-SPEC's own claim, independently verified):** `frontend/src/api/admin/exportExcel.ts::scaricaExcel(path)` (generic, path-parametrized, zero changes needed), `frontend/src/components/admin/FlatImportDialog.tsx` (generic, `risorsa: string` prop, zero changes needed), `frontend/src/components/admin/DiffPreviewTable.tsx` (generic, zero changes needed — already renders the `riga_modificata_dopo_export` amber badge D-11 needs).

## Open Questions

1. **Colonne esatte del foglio `effetti` e riferimento al genitore**
   - Cosa sappiamo: `EffettoOpzione` non ha chiave naturale; `forfait_arredo` (stessa forma, FK verso `OpzioneDomanda`) usa `opzione_id` numerico + colonna di contesto `opzione_etichetta` sola lettura.
   - Cosa non è chiaro: se il planner vuole che l'admin scriva `opzione_id` a mano in Excel per un nuovo effetto (numero opaco, in tensione con D-33 "mai un id numerico" — ma D-33 parla della **tabella nella pagina web**, non del file Excel, quindi non è necessariamente in conflitto) oppure preferisce un riferimento testuale `domanda_code`+`opzione_code` risolto a `opzione_id` internamente.
   - Raccomandazione: usare `opzione_id` numerico (A1 sopra), coerente con `forfait_arredo`, e lasciare `domanda_code`/`opzione_code` come colonne di contesto sola lettura per la leggibilità a schermo — il planner può girare questa scelta senza impatto architetturale.

2. **`derivazioni`: import crea nuove righe o solo modifica quelle esistenti?**
   - Cosa sappiamo: D-06 vuole che l'Excel sia "l'unico modo" di curare le derivazioni; la tabella ha sia `id` sia un vincolo naturale a 4 colonne.
   - Cosa non è chiaro: se "l'unico modo" implica anche creare nuove derivazioni da riga senza `id` (coerente con D-04 di default) o se questo sheet, essendo l'unico a 4 colonne di identità composta, merita una regola più stretta.
   - Raccomandazione: default a D-04 standard (riga senza id + parent esistenti = crea), a meno che l'utente non chieda diversamente in fase di piano.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Import di un file `domande` che riattiva silenziosamente un'opzione con dipendenza rotta, bypassando il controllo admin | Tampering | La guardia D-28 (Pitfall 4) deve essere applicata anche nel percorso import, non solo nel PATCH — un file caricato da un admin **legittimo** ma distratto non deve poter rompere silenziosamente una derivazione attiva |

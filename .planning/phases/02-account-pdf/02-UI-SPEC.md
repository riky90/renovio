# Phase 2 — UI Design Contract

> Visual and interaction contract for Account & PDF (registrazione/login, sessione, storico stime, download PDF Free). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Language of all UI copy: Italian.** Design system already exists from Phase 1 — this document **extends** `01-UI-SPEC.md`, it does not reinvent it. All Phase 1 tokens (spacing, typography, color) carry over unchanged unless a delta is stated.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn — **already initialized** (`frontend/components.json` present) |
| Preset | `radix-vega`, base color **Slate**, CSS variables enabled, no prefix |
| Component library | radix (via shadcn/ui) |
| Icon library | lucide-react |
| Font | Inter (variable) — system-ui fallback stack (unchanged from Phase 1) |

**shadcn components already installed and reused in Phase 2:** `input`, `label`, `button`, `card`, `alert`, `separator`, `badge`, `skeleton`, `popover`, `command`, `radio-group`, `dialog`, `input-group`, `textarea`. All shadcn official registry.

**New shadcn components required for Phase 2** (shadcn official registry only — no third-party):
- `avatar` — account menu trigger (user initials, since no photo upload in v1).
- `dropdown-menu` — account menu (name, "Le mie stime", "Esci").
- `form` (shadcn form primitives, react-hook-form + zod) — recommended for registration/login/reset validation; if the planner prefers the existing hand-rolled validation pattern from `EstimateForm.tsx` (no `form` primitive used there), that is an acceptable equivalent — **not a hard requirement**, contract cares about the resulting states, not the library.

**Net-new frontend dependency implied (not yet in `package.json`):** a client-side router (react-router recommended) is required to serve distinct auth/account screens (see Screen Contracts below). This is an architecture decision for the planner/researcher, not itself a visual contract item — flagged here only because it changes the app shell from single-page to multi-route.

## Spacing Scale

Unchanged from Phase 1 — 8-point scale, reused as-is.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, adornment padding |
| sm | 8px | Compact spacing (label→input, badge padding) |
| md | 16px | Default gap between form fields and inside cards |
| lg | 24px | Card inner padding, gap between list rows |
| xl | 32px | Section breaks (form → footer links, header → content) |
| 2xl | 48px | Page top/bottom padding on desktop |
| 3xl | 64px | Not used in Phase 2 screens (kept for landing-scale rhythm only) |

**Exceptions (carried over + one addition):** interactive touch targets (buttons, inputs, dropdown-menu rows, storico list rows) have a **minimum height of 44px**. New: the account-menu avatar trigger is a 40px circular hit target (below 44px) — acceptable exception because it sits in a header with adjacent padding that brings the effective tap area to ≥44px.

## Typography

Unchanged from Phase 1 — Inter, exactly 2 weights (400 regular, 600 semibold), exactly 4 roles. Reused verbatim for every Phase 2 screen (auth forms, account menu, storico list, PDF).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.3 |
| Display | 30px | 600 | 1.2 |

- **Body** — field helper/error text, disclaimer/legal microcopy ("Continuando accetti..."), empty-state body, storico row secondary line (data, mq, tipo).
- **Label** — field labels (Email, Password, Nome), button text, storico row primary line (città + totale).
- **Heading** — screen titles ("Accedi", "Crea il tuo account", "Le mie stime", "Reimposta la password").
- **Display** — not used on auth/account screens (no large numeric hero there); still used on the read-only snapshot detail view for the total range, reusing the Phase 1 result-screen contract exactly.

PDF typography (see Screen & Component Contracts §F) reuses the same two weights and a compatible size ramp scaled for print, not the on-screen px values verbatim.

## Color

Unchanged from Phase 1 — single accent, 60/30/10 split, base **Slate**, accent **blue-600**. No new hue introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F8FAFC` (slate-50) | Page background on all Phase 2 screens |
| Secondary (30%) | `#FFFFFF` on `#E2E8F0` borders (slate-200) | Auth form card, account dropdown panel, storico row cards, snapshot detail cards |
| Accent (10%) | `#2563EB` (blue-600) | See reserved list below |
| Destructive | `#DC2626` (red-600) | Validation/auth error messaging only |

**Text colors (neutral, not counted in 60/30/10):** primary `#0F172A` (slate-900), secondary/muted `#64748B` (slate-500), on-accent `#FFFFFF`.

**Accent (`#2563EB`) reserved exclusively for, in Phase 2:**
1. Primary CTA per screen — exactly one per screen: "Crea account" (registration), "Accedi" (login), "Invia link di reset" (password dimenticata), "Imposta nuova password" (reset), "Scarica PDF" (result/storico detail — replaces the neutral placeholder it had in Phase 1's `SoftWallCta`).
2. Input focus ring (all text inputs — unchanged behavior from Phase 1).
3. Active/current-page indicator in the account dropdown menu (if shown) and the account avatar ring when the menu is open.
4. Text links inline ("Password dimenticata?", "Non hai un account? Registrati", "Hai già un account? Accedi").

Accent is **never** applied to: the Google OAuth button (uses its own neutral/outline treatment, see Copywriting), the storico list rows, the account-menu trigger avatar background (slate, not blue), or more than one CTA per screen.

**Amber info tone** (unchanged from Phase 1: `#FFFBEB` bg / `#FCD34D` border / `#B45309` text) reused for: "Ti abbiamo inviato un'email con le istruzioni" (reset-link-sent confirmation) and the fallback-listino disclaimer inside the read-only snapshot view (carried unchanged from the frozen snapshot).

**Destructive (`#DC2626`) reserved for:** field-level and form-level auth errors (credenziali non valide, email già registrata, link scaduto). **No destructive-action button exists in Phase 2** (no account deletion, no estimate deletion in scope) — the destructive token is validation-only here too, same as Phase 1.

**Contrast:** all pairs meet WCAG AA, identical to Phase 1 verification (blue-600/white, slate-900/slate-50, red-600/white, amber-700/amber-50).

The `dialog` component installed in the codebase is therefore **not** used for a destructive-confirm pattern in Phase 2; if the planner needs it for something else (e.g. a lightweight "stima salvata" confirmation), that is an acceptable secondary use but not contractually required.

## Screen & Component Contracts

Extends Phase 1's Input flow and Result screen contracts (`01-UI-SPEC.md` §A/§B), which remain valid unchanged. The following are net-new for Phase 2.

### A. Soft-wall gate → auth handoff (modifies `SoftWallCta.tsx`)

The existing `SoftWallCta` component's four buttons change behavior for two of the four (per D-07/D-10; "Passa a Pro" and "Contatta un professionista" remain soft-wall/deferred — Phase 3/4):

- **"Scarica PDF"** and **"Salva / crea account"**, when clicked **while anonymous**, navigate to the registration screen (§B) carrying an intent flag: `save` (silent save) or `save+download` (save then auto-trigger PDF). The in-browser current estimate result (already held in `EstimatePage` state) is the payload that gets persisted once the account exists — no re-calculation.
- **"Passa a Pro"** and **"Contatta un professionista"** keep the Phase 1 soft-wall feedback ("Disponibile a breve...") — unchanged, still deferred to Phase 3/4.
- When the user is **already logged in** and lands on the result screen, "Scarica PDF" and "Salva / crea account" change meaning: "Salva / crea account" is hidden/replaced (the estimate auto-saves per D-07, no button needed — see success line above), and "Scarica PDF" becomes a direct, immediate download (no navigation), matching the button contract in §F below.

### B. Registration screen (`/registrati`)

Single centered card, `max-width: 400px`, same page chrome (slate-50 background) and vertical rhythm (`xl` gaps) as the Phase 1 input screen. Layout top to bottom:

1. Heading (Heading size): "Crea account e salva la stima" if arriving from a soft-wall intent, otherwise "Crea il tuo account".
2. Fields in order: **Nome**, **Email**, **Password** (input-group with a show/hide-password trailing icon adornment, reusing the installed `input-group` component). Inline validation on blur, per the validation copy table above.
3. Primary CTA (accent, full-width, 44px min-height): "Crea account".
4. Divider "oppure".
5. Google button (outline/neutral variant, full-width, Google "G" icon from lucide or brand asset): "Continua con Google".
6. Footer link: "Hai già un account? Accedi" → navigates to `/accedi`, preserving any pending save/download intent.
7. On success: if intent included `save`, show the inline confirmation "Stima salvata nel tuo account."; if intent included `download`, immediately trigger the PDF download flow (§F) after redirect to the result/detail view.

### C. Login screen (`/accedi`)

Same card shell as §B. Fields: **Email**, **Password**. Primary CTA (accent): "Accedi". Link "Password dimenticata?" (accent text link, right-aligned under the password field). Divider + Google button ("Accedi con Google"), same treatment as §B. Footer link: "Non hai un account? Registrati". Auth failure renders a destructive `alert` above the fields with the "credenziali non valide" copy — form fields are not cleared, focus returns to email.

### D. Password reset flow

Two screens, same card shell:
- **`/password-dimenticata`** — single Email field + primary CTA "Invia link di reset". On submit, always shows the amber info confirmation "Ti abbiamo inviato un'email con le istruzioni..." (regardless of whether the email exists, to avoid leaking account existence) — replaces the form.
- **`/reimposta-password?token=...`** — single "Nuova password" field (input-group, show/hide) + primary CTA "Imposta nuova password". Invalid/expired token renders the destructive alert "Il link non è più valido. Richiedine uno nuovo." with a link back to `/password-dimenticata`, form not shown. On success, redirect to `/accedi` with a one-time inline success line above the login form.

### E. Header / account state (global, all screens once auth exists)

Replaces the plain "ristruttura-stima" static title in `EstimatePage.tsx` with a header row: title left-aligned, account state right-aligned.
- **Anonymous:** neutral/outline "Accedi" button in the header, `sm`-height, top-right.
- **Logged in:** `avatar` (slate background, accent ring when menu open, user initials from Nome — e.g. "MR" for "Marco Rossi") as a `dropdown-menu` trigger, top-right. Menu items: user's name + email (non-interactive header row, Body muted), separator, "Le mie stime" (navigates to §F below), separator, "Esci" (logout — clears the httpOnly session cookie server-side, then redirects to the anonymous input screen).

### F. "Le mie stime" — storico screen (`/le-mie-stime`)

Centered column, same `max-width: 640px` constraint as the result screen.

1. Heading: "Le mie stime".
2. **List of saved estimates**, newest first, one card-row per estimate (secondary surface, `md` padding, `sm` gap between rows): città + totale range (Label size, tabular-nums) on the primary line, mq · tipo · data (Body muted) on the secondary line. Entire row is a tap target → navigates to the read-only snapshot detail (reuses the Phase 1 §B result-screen layout exactly: summary panel, optional fallback disclaimer, 4 category cards, total emphasis panel — all rendered from the frozen snapshot, not recalculated) plus a **"Scarica PDF"** primary CTA at the bottom (replacing `SoftWallCta` on this read-only view — no soft-wall buttons here, the user is already authenticated).
3. **Empty state** (no saved estimates): centered message block — heading "Non hai ancora stime salvate", body copy from the table above, primary CTA "Nuova stima" (accent) → navigates to the anonymous input screen (`/`).
4. **PDF download button contract** (used here and on the live result screen once logged in): default label "Scarica PDF"; on click, label swaps to "Generazione in corso…" with a small inline spinner (button stays accent, disabled during generation, min 44px height preserved); on success the browser's native download starts, button reverts to default label; on failure, render the destructive-tone inline message "Non siamo riusciti a generare il PDF. Riprova tra qualche istante." below the button (not a full-page alert — this is a secondary action, do not disrupt the rest of the screen).

### G. States (additions to Phase 1's state table)

| State | Treatment |
|-------|-----------|
| Auth form submitting | Primary CTA shows a disabled/loading state (same visual pattern as the Phase 1 "Calcola la stima" disabled state — muted, non-accent, spinner optional) while the request is in flight. |
| Auth error (invalid credentials / email exists) | Destructive `alert` above the form fields, form values preserved. |
| Session check (app boot) | Brief `skeleton` in the header account-slot only, while the current-session check resolves; never block or skeleton the rest of the page. |
| Storico loading | `skeleton` rows (3–4 placeholder rows matching the row height) in place of the list. |
| Storico empty | Empty-state block per §F.3. |
| PDF generating | Inline button loading state per §F.4 — never a full-page overlay. |
| PDF error | Inline destructive text under the button per §F.4 — never blocks the rest of the screen. |

### H. PDF document branding (PDF-01, D-11/D-12)

Not a screen, but a binding visual contract for the server-side generated document (1 page, A4):

- **Palette:** same Slate/blue-600 tokens as the web app — header band or accent rule in blue-600, body text slate-900 on white, muted labels slate-500. No new PDF-only palette.
- **Header:** logo placeholder (top-left, acceptable as text wordmark "ristruttura-stima" in Label/Heading weight if no logo asset supplied) + the user's name (Body) + generation date, top-right.
- **Body, top to bottom:** riepilogo input (città · mq · tipo, styled as a compact key-value block, not the on-screen pill/badge treatment which doesn't print well) → fallback disclaimer (amber-toned box, only if `fallback=true` on the snapshot) → 4 category cards as a simple 2×2 or stacked table (range values right-aligned, tabular figures) → total emphasis block (blue-600 accent, largest text on the page, IVA-inclusa label) → footer disclaimer/legal line ("Stima indicativa, non sostituisce un sopralluogo professionale.") + filename note.
- **Filename:** `stima-ristrutturazione-<citta>-<data>.pdf` (slugified città, date as `YYYY-MM-DD`), per D-12.
- **Domain guard (binding, carried from Phase 1 CLAUDE.md rule 1 / D-13):** the PDF template must never render `coefficiente_impresa`, `base_eur_mq`, moltiplicatori, or `prezzo_impresa` — only the same range values already exposed in the API/snapshot. This is a server-side template contract, not just a UI one, but it is listed here because it is part of the same anti-leak guard verified by Phase 1's test suite pattern (`test_no_leak.py`) and must be re-verified for the PDF output.

## Open Questions (non-blocking — reasonable defaults/assumptions set above)

1. **Modal vs. dedicated pages for auth** — CONTEXT.md left this to discretion. This spec defaults to **dedicated routes** (`/registrati`, `/accedi`, `/password-dimenticata`, `/reimposta-password`, `/le-mie-stime`) rather than modals, because the forms are multi-field and reset/registration benefit from shareable, bookmarkable, back-button-friendly URLs; it also keeps the anti-leak-tested result screen untouched. Requires adding a router (react-router recommended) — a net-new dependency the planner should confirm. If the planner strongly prefers a modal-based flow instead (using the already-installed `dialog` component and no router), that is an acceptable alternative that does not violate any token in this contract — only §B–§F's "screen" framing would become "modal" framing.
2. **Google icon asset** — defaulted to a neutral/outline button with a standard "G" glyph (lucide has no official Google logo; a small inline SVG brand asset is acceptable and does not count as a third-party registry block).
3. **Avatar initials algorithm** — first letter of Nome + first letter of Cognome if present, else first two letters of Nome; not a blocking visual decision, executor's choice.
4. **PDF library visual fidelity** — WeasyPrint (HTML/CSS → PDF) is the natural choice to reuse the same Tailwind-adjacent slate/blue tokens via a print stylesheet; reportlab would require re-declaring colors/spacing manually. This is a technical choice for the planner (per CONTEXT.md discretion) but is noted here because it affects how faithfully §H's branding contract can be executed.

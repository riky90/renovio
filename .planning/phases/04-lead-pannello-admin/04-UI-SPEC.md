# Phase 4 — UI Design Contract

> Visual and interaction contract for Lead & pannello admin (contact/lead form on Free+Pro result screens, protected `/admin` area with Lead dashboard, listini/prezzi, coefficienti, città/testi, referenti CRUD, and the two-step Excel upload/diff flow). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Language of all UI copy: Italian.** Design system already exists from Phase 1 (`01-UI-SPEC.md`), Phase 2 (`02-UI-SPEC.md`) and Phase 3 (`03-UI-SPEC.md`) — this document **extends** all three, it does not reinvent them. All spacing, typography and color tokens carry over unchanged unless a delta is stated below (D-21: "Riusa componenti e stile delle Fasi 1-3 — palette Slate/blue-600, card, form"). Existing components `CategoryCard`, `TotalCard`, `FallbackDisclaimer`, `SoftWallCta`, `PdfDownloadButton`, `AccountMenu`, `DettaglioProView` are reused as-is; only `SoftWallCta` gains new behavior for its "Contatta un professionista" button.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn — **already initialized** (`frontend/components.json`) |
| Preset | `radix-vega`, base color **Slate**, CSS variables enabled, no prefix (unchanged) |
| Component library | radix (via shadcn/ui) |
| Icon library | lucide-react |
| Font | Inter (variable) — unchanged from Phase 1/2/3 |

**shadcn components already installed and reused in Phase 4:** `accordion`, `alert`, `avatar`, `badge`, `button`, `card`, `command`, `dialog`, `dropdown-menu`, `input`, `input-group`, `label`, `popover`, `radio-group`, `separator`, `skeleton`, `textarea`.

**New shadcn components required for Phase 4** (shadcn official registry only — no third-party):
- `table` — admin Lead list, listini/voci CRUD grids, referenti list, Excel diff preview rows. This is the primary net-new primitive this phase needs; nothing else in the admin area requires anything beyond composition of existing primitives.
- `tabs` — the `/admin` section navigation on mobile/narrow widths (sidebar on desktop, see §B).
- `select` — dropdown pickers (lead filters by città/stato, tipo di ristrutturazione picker in CRUD forms, città picker).
- `switch` — boolean toggles (`attivo` flag on Referente rows, any on/off field in CRUD forms) instead of a checkbox, for clearer at-a-glance state in a dense table row.
- `alert-dialog` — destructive-confirmation pattern (delete referente / delete voce / delete listino row, discard upload). Distinct from the existing `dialog` (which stays reserved for non-destructive modal flows, e.g. the upload diff-preview step).
- `sonner` (toast) — lightweight non-blocking confirmations for admin CRUD saves ("Modifica salvata") and the lead-send confirmation on the user-facing side, complementing (not replacing) the inline confirmation copy already mandated below.

No third-party registries are proposed. Registry vetting gate: not applicable.

## Spacing Scale

Unchanged from Phase 1/2/3 — 8-point scale, reused as-is.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, table cell internal padding (vertical) |
| sm | 8px | Compact spacing (label→input, badge padding, table cell padding horizontal) |
| md | 16px | Default gap between form fields, inside cards, between admin sidebar nav items |
| lg | 24px | Card inner padding, gap between admin section header and table, gap between lead list and detail panel |
| xl | 32px | Section breaks (lead form → confirmation, admin sidebar → content column) |
| 2xl | 48px | Page top/bottom padding on desktop |
| 3xl | 64px | Not used in Phase 4 screens |

**Exceptions (carried over + one addition):** interactive touch targets (buttons, inputs, dropdown rows) keep the **minimum 44px** height. New: admin **table rows** are a desktop-first, information-dense surface and may be as compact as **40px** row height (below the 44px rule) — acceptable because the admin area is an internal tool used on desktop/tablet, not a public mobile-first flow; the row's actual interactive controls (edit/delete icon buttons within the row) still get a 32–36px hit target with adequate hit-slop, and any row that is itself the full tap target (e.g. mobile-stacked list rows, per §C.2) reverts to the 44px minimum.

## Typography

Unchanged from Phase 1/2/3 — Inter, exactly 2 weights (400 regular, 600 semibold), exactly 4 roles. No new size introduced for admin tables — density comes from spacing/line-height, not a 5th font size.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.3 |
| Display | 30px | 600 | 1.2 |

- **Body** — lead form helper text, empty-state body, table cell values that are prose (messaggio, note), disclaimer/legal microcopy.
- **Label** — field labels, table header cells, table cell values that are numeric/coded (totale stima, prezzo, coefficiente, stato badges), sidebar nav item text, button text.
- **Heading** — screen/section titles ("Contatta un professionista", "Lead", "Listini e prezzi", "Coefficienti", "Città e testi", "Referenti"), lead detail panel title, admin section headers.
- **Display** — not introduced net-new in Phase 4; no large hero number in the admin area. The lead-form estimate snapshot reuses **Heading** size for the range figure (not Display) — it is supporting context on the form, not the page's hero number.

Table cell text uses **Label** (14px/600) for numeric/coded columns and **Body** (16px/400) for prose columns, both with `tabular-nums` on any numeric column (prezzi, coefficienti, totali, quantità) so figures align vertically — same discipline as the category cards in Phase 1.

## Color

Unchanged from Phase 1/2/3 — single accent, 60/30/10 split, base **Slate**, accent **blue-600** (`#2563EB`). No new hue introduced; the existing amber info tone and destructive red are reused for the diff-preview 3-way state (see below) rather than inventing green/yellow traffic-light colors.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F8FAFC` (slate-50) | Page background on the lead form and all `/admin` screens |
| Secondary (30%) | `#FFFFFF` on `#E2E8F0` borders (slate-200) | Lead form card, admin sidebar panel, table container, CRUD form cards, upload diff-preview panel |
| Accent (10%) | `#2563EB` (blue-600) | See reserved list below |
| Destructive | `#DC2626` (red-600) | Destructive confirmations + upload error rows + validation errors |

**Text colors (neutral, not counted in 60/30/10):** primary `#0F172A` (slate-900), secondary/muted `#64748B` (slate-500), on-accent `#FFFFFF`.

**Accent (`#2563EB`) reserved exclusively for, in Phase 4 — additions to the Phase 1/2/3 list:**
1. Primary CTA "Invia richiesta" on the lead contact form.
2. Primary CTA per admin CRUD form: "Salva {entità}" (e.g. "Salva referente") / "Carica listino" / "Conferma import" / "Aggiungi referente" — exactly one primary accent action per admin screen/dialog, matching the existing single-primary-CTA discipline.
3. The active sidebar/tab nav item in `/admin` (accent left border + accent text on the active section, e.g. "Lead" highlighted while on `/admin/lead`).
4. The **"nuovo"** lead-status badge (accent-tinted `bg-primary/10 text-primary`, not solid fill — reserves solid accent fill for buttons only) — draws attention to unhandled leads in the dashboard list.
5. The **"Nuove righe"** diff-preview count/badge on the upload confirmation screen (accent-tinted, same treatment as #4) — signals net-new data, not a warning.

Accent is **never** applied to: table row backgrounds/zebra-striping, the sidebar nav container itself (only the active item's text/border), the "gestito" status badge, more than one CTA per admin dialog, or decorative table borders.

**Diff-preview 3-way state (net-new semantic use, no new hue — reuses existing 3 semantic colors):**
- **Righe nuove** → accent-tinted badge/row marker (see #5 above).
- **Righe modificate** → **amber** info tone (unchanged: `#FFFBEB` bg / `#FCD34D` border / `#B45309` text) — a change is informational, not an error, consistent with its existing use for the fallback-listino disclaimer and Pro targeted-question helper notes.
- **Righe scarto/errore** → **destructive** red (`#DC2626`), listed in a dedicated "Scarti" panel below the diff table with the specific reason per row.

**Lead status badges (net-new semantic use, no new hue):** "nuovo" → accent-tinted (see #4); "gestito" → **neutral slate** badge (`bg-muted text-muted-foreground`, slate-100/slate-500) — handled leads recede visually, unhandled ones stand out. No third status color.

**Destructive (`#DC2626`) reserved for:** the `alert-dialog` destructive-confirm pattern (delete referente / delete voce / delete listino row / discard pending upload), upload scarti rows, and all existing validation-error uses carried from Phase 1–3.

**Contrast:** all pairs meet WCAG AA, identical basis to Phase 1/2/3 verification.

## Screen & Component Contracts

Extends Phase 1 §A/§B, Phase 2 §A–§H, Phase 3 §A–§E unchanged. The following are net-new for Phase 4.

### A. Lead contact form (attached to Free and Pro result screens — modifies `SoftWallCta.tsx`)

- **"Contatta un professionista"** stops being a soft-wall toast (Phase 1/3 deferred behavior) and becomes real:
  - **Anonymous user:** unchanged soft-wall-style gate — but per D-01 the feature requires login, so clicking routes to `/registrati?intent=contatta` (or `/accedi`, same save-at-signup-intent mechanism from Phase 2 §A), preserving the current on-screen estimate exactly like the existing PDF/save intents. No new routing pattern.
  - **Logged-in user (Free or Pro):** opens the lead form as a `dialog` (not a new route) anchored to the current result screen — keeps the user's estimate context on screen behind the modal, matches the low-friction, single-purpose nature of the form. `max-width: 480px` dialog, same card chrome as auth screens.
- **Form layout** (top to bottom inside the dialog): Heading "Contatta un professionista" + subheading (Body, muted) → **Nome** + **Email** inputs, prefilled from the account (`useAuth().user`), editable → **Telefono** input (`inputmode="tel"`) → **Preferenza di contatto** (`radio-group`, reusing the exact visual pattern of the Phase 1 tipo-di-ristrutturazione selector: Email / Telefono) → **Fascia oraria preferita** (`select`, optional, e.g. mattina/pomeriggio/sera — exact option set at planner's discretion) → **Messaggio** (`textarea`, optional, 3 rows) → **estimate snapshot note** (secondary-surface compact panel, Body, showing città/mq/tipo/range — reuses the Phase 2 §F storico-row visual pattern, read-only, not editable) → primary CTA (accent, full-width, 44px) "Invia richiesta".
- **On success:** dialog content swaps to an inline on-screen confirmation (Heading "Richiesta inviata" — reuse the payment-stub-success visual pattern from Phase 3 §B.5 — + the send-success copy + a "Chiudi" neutral button) **and** a `sonner` toast fires with the short confirmation. Dialog does not auto-close instantly (avoids the confirmation being missed) — user closes via "Chiudi" or clicking outside.
- **On error:** destructive inline text below the CTA (same pattern as `PdfDownloadButton`/payment-stub error, Phase 2/3), form values preserved, dialog stays open.
- **Domain guard (binding):** the estimate-snapshot note and every payload sent by this form render/transmit **only** the range values already used elsewhere on the result screen (città, mq, tipo, category/total ranges) — never `coefficiente_impresa`/`base_eur_mq`/prezzi impresa (D-22, CLAUDE.md rule 1). This applies identically whether the snapshot comes from the Free or the Pro result screen.

### B. `/admin` area shell (D-21)

Desktop-first (internal tool), responsive down to tablet; on mobile the sidebar collapses to the `tabs` component (horizontal scroll) rather than an off-canvas drawer, keeping the component surface small.

- **Desktop/tablet (≥768px):** persistent left sidebar (secondary surface, `w-64`, `md` internal padding), fixed nav list of the 5 sections (Lead, Listini e prezzi, Coefficienti, Città e testi, Referenti) each as a `Label`-size nav row with a lucide icon (e.g. `Inbox`, `Tags`, `SlidersHorizontal`, `MapPin`, `Users`), `md` vertical padding per row, min 44px row height. Active item: accent left border (3px) + accent text, inactive: slate-900 text, hover: slate-100 background. Content column to the right, `lg` padding, `max-width` none (admin tables can use the full remaining width, unlike the constrained 480–640px user-facing columns).
- **Mobile (<768px):** sidebar replaced by a horizontal `tabs` bar (same 5 labels, no icons to save space) pinned below the header, content stacks full-width below it.
- **Header row** (shared with the rest of the app): reuses the existing `AccountMenu`/logged-in header pattern from Phase 2 §E — the admin's avatar/dropdown is identical, no separate admin header design. A small **"Admin"** `badge` (neutral slate, not accent — this is an identity marker, not a call to action) sits next to the app wordmark only while inside `/admin`, so the operator always knows which mode they're in.
- **Guard UI:** a non-admin user who reaches `/admin` (deep link, stale bookmark) sees a centered single-column message (same shell as an empty state): Heading "Accesso negato" *(internal, not in copy table above as it's an edge case, not a primary flow)* + Body "Non hai accesso a questa sezione." + a neutral CTA back to `/`. Server-side `require_admin` is the real gate (403); this is the client-side rendering of that state, never a flash of real admin data.

### C. Lead dashboard (`/admin/lead`, ADM-04/D-17)

- **List view:** `table` component (secondary surface container, `lg` padding around it, no padding inside the table itself — rows go edge-to-edge within the card). Columns, left to right: **Data** (gg/mm/aaaa) · **Città** · **Nome** · **Contatti** (email + telefono stacked, Body small) · **Totale stima** (range, tabular-nums, right-aligned) · **Stato** (badge, "nuovo"/"gestito" per Color section above). Row height 40px (per Spacing exception), entire row is a click target opening the detail. Header row: Label size, slate-500, bottom border slate-200, sticky on scroll for long lists.
  - **Filters row** above the table: two `select` dropdowns ("Filtra per città", "Filtra per stato"), inline, `sm` gap, reset-filters text link when any filter active.
  - **Empty state** (no leads at all, ignoring filters): centered block per the empty-state copy table, no illustration needed (text-only, consistent with Phase 2's "Le mie stime" empty state).
  - **Empty state (filtered, zero matches):** a lighter inline message inside the table container ("Nessun lead corrisponde ai filtri selezionati.") + a "Rimuovi filtri" text link — distinct from the true-empty state so the operator knows filters are the cause, not an empty system.
- **Detail view:** opens as a `dialog` (`max-width: 560px`) or a right-side panel — planner's choice, visual contract identical either way (see Open Questions). Contents top to bottom: Heading (nome del lead) + data + città (Body muted) → **"Dati di contatto"** section (Label heading + key-value rows: email, telefono, preferenza, fascia oraria, messaggio) → **"Stima allegata"** section, reusing the exact Phase 1 §B card layout at reduced scale (input summary pills + 4 category-range rows or the frozen total, whichever the snapshot stored — full parity with the user-facing range, D-23) → **"Nota interna"** section (`textarea` + a `select` or `switch`-pair for stato nuovo/gestito, **"Salva nota e stato"** accent CTA, `sonner` success toast). No accent anywhere in the detail body except the "Salva nota e stato" button and the (already-established) "nuovo" badge if still unhandled.

### D. Admin CRUD sections — shared pattern (Listini e prezzi, Coefficienti, Città e testi, Referenti — ADM-01/02/03/04)

One consistent pattern reused across all four sections, so the operator learns it once:

1. **Section header:** Heading (section title) + primary accent CTA top-right ("Aggiungi {entità}") + (Listini e prezzi only) a secondary neutral/outline CTA "Carica listino da Excel" opening the upload flow (§E).
2. **Table:** same `table` component/row-height/typography discipline as §C. Columns vary per entity (e.g. Listini/voci: codice · descrizione · UM · prezzo cliente · **coefficiente impresa** · categoria; Coefficienti: tipo × categoria grid or list; Città e testi: comune · listino mappato · [separately] chiave testo · valore; Referenti: nome · email · telefono · città/listino · attivo (`switch`) · priorità). Each row ends with two icon-button actions (Modifica, Elimina) at 32–36px hit targets, `sm` gap between them. **Accessibility (binding, addresses the checker's Visuals recommendation):** because these two row actions are icon-only (no visible text label), each button MUST carry an explicit `aria-label` matching its tooltip text — `aria-label="Modifica"` and `aria-label="Elimina"` — so the tooltip string is not merely a hover affordance but also the button's accessible name. No icon-only button in the admin tables ships without this attribute.
3. **Row edit:** opens a `dialog` (not a full navigation, not inline-editable cells — keeps validation and the admin-only sensitive fields like `coefficiente_impresa`/`base_eur_mq` clearly scoped to an explicit edit action rather than always-visible inline inputs) with the entity's fields as a standard form (same `input`/`label`/`select`/`switch`/`textarea` primitives as the rest of the app), primary CTA **"Salva {entità}"** (accent, e.g. "Salva referente"), secondary **"Annulla modifica"** (neutral). On save: `sonner` toast "Modifica salvata", dialog closes, table refreshes.
4. **Row delete:** `alert-dialog` per the Destructive Actions table above — destructive button "Elimina {entità}", cancel "Annulla" (bare, 1:1-paired in the same dialog).
5. **Empty state:** per the CRUD empty-state copy, same visual block as §C's true-empty state, with the "Aggiungi {entità}" CTA repeated inline if the header CTA was scrolled out of view.
6. **Admin-only sensitive fields (D-10):** `coefficiente_impresa` and `base_eur_mq` render as normal fields **only inside `/admin`** dialogs/tables — never styled with any special "danger" visual treatment (they are ordinary business data to the admin, not a warning), but they must be physically absent from any non-admin-facing component, page, or API-shaped payload reused elsewhere in the app (binding domain guard, same as §A).

### E. Excel upload — two-step diff preview flow (D-18/D-19/D-20)

A dedicated `dialog` flow (large, `max-width: 720px`, scrollable body) launched from the "Carica listino da Excel" CTA in §D (Listini e prezzi section):

1. **Step 1 — Upload:** dropzone (`card`, dashed slate-300 border, centered icon + the dropzone copy + "oppure sfoglia i file" as a text-link triggering the native file picker), constraint note (Body muted) below it. On file select: client-side type/size check → if invalid, destructive inline message per copy table, dropzone stays; if valid, shows the filename + a `skeleton`/spinner "Verifica del file in corso…" while the backend parses and computes the diff.
2. **Step 2 — Diff preview:** replaces the dropzone with: a summary row of 3 count badges (nuove/modificate/scartate, per the Diff-preview 3-way state color contract) → a `table` listing the changed rows (colonna/voce, valore precedente → valore nuovo where applicable, badge per riga: Nuova/Modificata) → a separate **"Righe scartate"** panel (destructive-toned `alert` or a collapsed `accordion` item if the list is long) listing each discarded row with its specific reason (Body, destructive text) — never a bare count with no detail, per D-19's "elencate all'admin per correzione". Footer: **"Annulla import"** (neutral, triggers the discard `alert-dialog`) + **"Conferma import"** (accent, primary, disabled while zero valid rows exist).
3. **Step 3 — Result:** on confirm, `sonner` success toast with the import count, dialog closes, table in §D refreshes to reflect the new/updated rows; on backend failure, destructive inline message inside the dialog (import error copy), dialog stays open so the admin doesn't lose the preview.

This same two-step shell is reusable verbatim for any future bulk-upload entity — only the diff-table columns change.

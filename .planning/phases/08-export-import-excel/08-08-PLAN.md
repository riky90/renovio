<objective>
D-11. L'export porta gia' il suo timestamp di generazione; adesso la preview lo usa: riga
per riga dichiara cosa e' cambiato nel database **dopo** quel momento, e l'admin decide.
Nessun blocco duro — la preview esiste proprio per far vedere cosa si sta per rompere, non
per impedirlo.

Purpose: senza questo, due sessioni di curatela che si sovrappongono si sovrascrivono in
silenzio. Con questo, chi ricarica un file di ieri vede esattamente quali righe sta per
riportare indietro.
Output: `updated_at` sulle tabelle curate, campo `riga_modificata_dopo_export` sul diff,
badge ambra e banner nella preview.

**Perche' serve una migrazione.** Oggi nessuna delle tabelle curate ha una data di
modifica: l'unico `updated_at` del progetto e' su `testo` (`models/testo.py:34`). Senza
quella colonna la domanda "questa riga e' cambiata dopo che hai scaricato il file?" non ha
risposta possibile.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| timestamp letto dal foglio `ISTRUZIONI` | e' un dato **dentro il file caricato**, quindi controllato dall'utente: non e' una fonte fidata |
| migrazione → database di produzione | nove `add_column` su tabelle che contengono la curatela e i lead reali |
| flag di staleness → decisione dell'admin | il flag informa, non autorizza |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-70 | Tampering | timestamp del file falsificato per nascondere le righe superate | accept | chi carica e' gia' admin o staff e potrebbe comunque applicare le stesse modifiche dal CRUD; il flag e' un aiuto alla decisione, non un controllo di sicurezza — documentarlo nella docstring perche' nessuno lo scambi per tale |
| T-08-71 | Tampering | timestamp malformato che fa esplodere il parsing | mitigate | `leggi_timestamp_export` restituisce `None` su valore illeggibile e il flag resta `False`: nessuna eccezione propagata, nessun 500 |
| T-08-72 | Denial of Service | confronto riga per riga che moltiplica le query | mitigate | l'`updated_at` va letto nella **stessa** query che gia' carica i record per il diff, non con una query per riga |
| T-08-73 | Tampering | migrazione che perde dati sulle nove tabelle | mitigate | solo `add_column` con `server_default`, nessun `alter` di colonna esistente; `tests/test_seed.py` e `test_seed_dettaglio.py` nel comando di verifica; `downgrade` speculare |
| T-08-74 | Information Disclosure | `updated_at` esposto in una risposta pubblica | mitigate | la colonna non viene aggiunta a nessuno schema Pydantic del layer pubblico: entra solo nel calcolo del diff lato admin |
| T-08-75 | Elevation of Privilege | reintroduzione di un blocco duro che cambia il comportamento deciso | mitigate | acceptance criterion che nessun `disabled` del confirm dipende dal flag: D-11 ha scartato il blocco, e l'implementazione non puo' reintrodurlo di soppiatto |
| T-08-SC | Tampering | installazioni npm/pip | mitigate | nessun pacchetto nuovo in questo piano |
</threat_model>
